# AiProfessor MVP 요구사항 명세서

- 문서 버전: v0.1 (초안)
- 작성일: 2026-11-02
- 대상 저장소: `AiProfessor`
- 제품 방향: PDF 교재로 자격증·전공 시험을 준비하는 개인 학습자를 위한 AI 학습 웹앱

## 1. 문서 목적

이 문서는 기존 Django 기반 AiProfessor의 핵심 학습 흐름을 Spring Boot와 React 기반 웹앱으로 재설계하기 위한 MVP 요구사항을 정의한다.

MVP의 목적은 기능을 많이 만드는 것이 아니라 다음 하나의 사용자 흐름을 실제 배포 환경에서 끝까지 동작시키는 것이다.

> 회원가입·로그인 → PDF 업로드 → 비동기 처리 → 근거가 있는 요약 → 문제 생성 → 답안 제출·채점 → 오답 재학습

기존 Django 프로젝트에서 확인된 PDF, 요약, 문제, 답안, 오답 및 비동기 처리 기능은 마이그레이션 참고 자료로 사용한다. Spring Boot 구현의 정확성, 성능, 장애 복구 및 RAG 품질은 새 프로젝트에서 별도로 검증한다.

## 2. 제품 목표

### 2.1 사용자 목표

사용자는 학습할 PDF 한 개를 업로드하고, 해당 문서만을 근거로 생성된 요약과 문제를 이용해 학습한 뒤 자신의 오답을 다시 풀 수 있어야 한다.

### 2.2 개발 목표

1. Spring Boot와 React로 완결된 웹 서비스를 구축한다.
2. 시간이 오래 걸리는 PDF·임베딩·LLM 처리를 비동기로 분리하고 작업 상태를 추적한다.
3. AI 결과에 PDF 페이지 근거를 제공해 사용자가 답변을 검증할 수 있게 한다.
4. 검색 품질과 생성 품질을 분리해 평가할 수 있는 최소 평가 체계를 만든다.
5. 인증, 데이터 소유권, 재시도, 삭제, 관측 가능성을 포함해 운영 가능한 기본 구조를 갖춘다.
6. 구현 과정과 실험 결과를 재현 가능한 문서와 블로그 글로 남긴다.

### 2.3 MVP 성공 기준

다음 조건을 모두 만족하면 MVP가 완료된 것으로 판단한다.

- 신규 사용자가 가입하고 로그인할 수 있다.
- 유효한 텍스트 PDF 한 개를 업로드하면 비동기 작업을 거쳐 `READY` 상태가 된다.
- 사용자는 처리 단계와 실패 사유를 확인하고, 재시도 가능한 실패는 다시 요청할 수 있다.
- 요약의 핵심 주장과 문제·해설에 원문 페이지 근거가 표시된다.
- 객관식과 주관식 문제를 생성하고 답안을 제출할 수 있다.
- 채점 결과, 해설, 근거 및 오답 기록을 확인하고 다시 풀 수 있다.
- 다른 사용자의 문서와 학습 데이터에는 접근할 수 없다.
- 문서를 삭제하면 관련 원문, 청크, 벡터, 요약, 문제 및 답안 데이터가 함께 삭제된다.
- 핵심 사용자 흐름이 테스트 및 배포 환경에서 검증된다.
- RAG 평가 결과와 테스트 조건이 문서로 남아 있다.

## 3. 대상 사용자와 핵심 시나리오

### 3.1 주요 사용자

- 자격증 시험을 준비하는 개인 학습자
- 전공 교재나 강의 자료로 시험을 준비하는 대학생
- 긴 PDF를 빠르게 구조화하고 문제 풀이로 복습하려는 사용자

### 3.2 대표 시나리오

1. 사용자가 이메일과 비밀번호로 가입하고 로그인한다.
2. 대시보드에서 PDF 한 개를 업로드한다.
3. 서버가 파일을 검증하고 작업 ID를 즉시 반환한다.
4. 사용자는 `업로드 완료 → 텍스트 추출 → 청킹 → 임베딩 → 완료` 상태를 확인한다.
5. 사용자가 문서 전체 요약 또는 특정 주제 요약을 생성한다.
6. 요약의 근거 페이지를 열어 원문과 대조한다.
7. 문제 유형, 개수 및 난이도를 선택해 문제를 생성한다.
8. 답안을 제출하고 채점 결과, 해설 및 원문 근거를 확인한다.
9. 틀린 문제 또는 헷갈린 문제를 오답 목록에서 다시 푼다.
10. 사용자가 문서를 삭제하면 파생 데이터도 삭제된다.

## 4. MVP 범위

### 4.1 포함 범위

- 이메일·비밀번호 회원가입, 로그인, 로그아웃 및 인증 갱신
- 사용자별 데이터 소유권과 접근 제어
- 텍스트 추출이 가능한 PDF 한 개 업로드
- 파일 형식, 크기, 페이지 수 및 중복 업로드 검증
- PDF 처리 작업의 비동기 실행, 상태 조회, 제한적 자동 재시도 및 수동 재시도
- 페이지 번호를 보존하는 텍스트 추출과 청크 생성
- 임베딩 생성과 벡터 검색
- 문서 전체 요약 및 선택 주제 요약
- 객관식·주관식 문제 생성
- 답안 제출, 채점, 해설 및 근거 표시
- 오답·헷갈린 문제 저장과 재학습
- 문서·요약·문제·답안 삭제
- API 명세, 핵심 테스트, 로그, 메트릭 및 배포
- 최소 RAG 평가 데이터셋과 결과 보고서

### 4.2 제외 범위

다음 기능은 MVP 완료 후 별도 단계에서 다룬다.

- PG 결제, 구독, 크레딧 및 환불
- 소셜 로그인, 이메일 인증 및 비밀번호 찾기
- 스캔 PDF OCR
- 여러 PDF를 하나의 과목으로 묶는 기능
- PPT, DOCX, 웹페이지, 음성 및 영상 입력
- 강사·교육기관용 관리자 대시보드
- 실시간 공동 학습, 댓글 및 공유
- 네이티브 모바일 앱
- 모델 파인튜닝
- 고급 추천, 학습 일정 및 간격 반복 알고리즘
- 운영자용 콘텐츠 검수 도구

## 5. 기능 요구사항

우선순위는 `P0`(MVP 필수), `P1`(시간이 허용되면 포함), `P2`(MVP 이후)로 구분한다.

### 5.1 인증과 사용자

| ID | 요구사항 | 우선순위 | 인수 조건 |
|---|---|---:|---|
| AUTH-001 | 이메일과 비밀번호로 회원가입한다. | P0 | 중복 이메일은 거부하고 비밀번호는 단방향 해시로 저장한다. |
| AUTH-002 | 로그인 후 보호 API를 사용할 수 있다. | P0 | 잘못된 자격 증명은 동일한 형태의 인증 오류로 응답한다. |
| AUTH-003 | 인증을 갱신하고 로그아웃할 수 있다. | P0 | 로그아웃한 갱신 토큰은 재사용할 수 없다. |
| AUTH-004 | 사용자는 본인의 문서와 학습 데이터만 조회·수정·삭제한다. | P0 | URL의 식별자를 변경해도 타인의 데이터에 접근할 수 없다. |
| AUTH-005 | 사용자 계정과 전체 데이터를 삭제할 수 있다. | P1 | 삭제 완료 후 원문과 모든 파생 데이터를 조회할 수 없다. |

### 5.2 PDF 업로드와 문서 관리

| ID | 요구사항 | 우선순위 | 인수 조건 |
|---|---|---:|---|
| DOC-001 | 사용자는 PDF 한 개를 업로드한다. | P0 | 서버는 확장자뿐 아니라 MIME·파일 시그니처를 검사한다. |
| DOC-002 | 파일 제한을 적용한다. | P0 | 기본 제한은 파일당 50MB·300페이지이며 설정으로 변경할 수 있다. |
| DOC-003 | 암호화·손상·빈 문서·텍스트가 없는 PDF를 식별한다. | P0 | 처리 실패 상태와 사용자가 이해할 수 있는 실패 사유를 제공한다. |
| DOC-004 | 문서 목록과 상세 정보를 조회한다. | P0 | 파일명, 업로드 시각, 페이지 수, 처리 상태와 실패 사유를 표시한다. |
| DOC-005 | 동일 사용자의 동일 파일 중복 업로드를 탐지한다. | P1 | 파일 해시를 기준으로 경고하고 기존 문서 사용 여부를 안내한다. |
| DOC-006 | 문서를 삭제한다. | P0 | 원문, 청크, 벡터 및 모든 학습 파생 데이터가 함께 삭제된다. |

### 5.3 비동기 처리

문서 처리 상태는 최소한 다음 상태를 가진다.

```text
UPLOADED → EXTRACTING → CHUNKING → EMBEDDING → READY
                                         ↘ FAILED
```

| ID | 요구사항 | 우선순위 | 인수 조건 |
|---|---|---:|---|
| JOB-001 | 업로드 요청과 문서 처리 작업을 분리한다. | P0 | 파일 저장이 끝난 뒤 API는 전체 AI 처리를 기다리지 않고 작업 식별자를 반환한다. |
| JOB-002 | 사용자는 작업 상태와 현재 단계를 조회한다. | P0 | 새로고침 후에도 상태가 유지된다. |
| JOB-003 | 일시적 외부 API·네트워크 오류를 자동 재시도한다. | P0 | 지수 백오프를 적용해 최대 3회 재시도하고 횟수를 기록한다. |
| JOB-004 | 동일 작업이 중복 실행되어도 결과가 중복 저장되지 않는다. | P0 | 작업 키와 데이터 제약으로 멱등성을 보장한다. |
| JOB-005 | 최종 실패 작업을 사용자가 수동 재시도한다. | P0 | 실패 원인을 보존하고 새 시도 이력을 남긴다. |
| JOB-006 | 처리 중 애플리케이션이 재시작되어도 작업을 복구한다. | P1 | 중단 작업을 탐지해 재개하거나 안전하게 실패 처리한다. |

### 5.4 RAG 수집과 검색

| ID | 요구사항 | 우선순위 | 인수 조건 |
|---|---|---:|---|
| RAG-001 | PDF에서 페이지 단위로 텍스트를 추출한다. | P0 | 각 텍스트 조각이 원본 문서와 페이지 번호를 유지한다. |
| RAG-002 | 설정 가능한 전략으로 텍스트를 청킹한다. | P0 | 청크 크기·겹침·전략과 임베딩 모델 정보를 기록한다. |
| RAG-003 | 청크 임베딩을 생성해 검색 가능한 형태로 저장한다. | P0 | 사용자 및 문서 범위를 벗어난 청크가 검색되지 않는다. |
| RAG-004 | 질문이나 주제에 관련된 청크를 검색한다. | P0 | 검색 결과에 문서 ID, 페이지, 청크 ID 및 점수가 포함된다. |
| RAG-005 | 동일 입력과 설정의 중복 임베딩 생성을 방지한다. | P1 | 문서 해시·청크 해시·모델 버전을 식별 기준으로 사용한다. |
| RAG-006 | 검색 전략을 교체·비교할 수 있다. | P1 | 기본 벡터 검색과 개선 전략의 평가 결과를 같은 데이터셋에서 비교한다. |

### 5.5 요약

| ID | 요구사항 | 우선순위 | 인수 조건 |
|---|---|---:|---|
| SUM-001 | 문서 전체의 구조화된 요약을 생성한다. | P0 | 핵심 개념, 세부 내용 및 학습 포인트를 구분해 제공한다. |
| SUM-002 | 사용자가 입력한 주제에 대한 요약을 생성한다. | P0 | 문서 근거가 부족하면 부족하다고 표시하고 내용을 만들어내지 않는다. |
| SUM-003 | 요약에 근거 페이지를 표시한다. | P0 | 사용자가 인용 근거를 눌러 해당 페이지와 추출 문맥을 확인할 수 있다. |
| SUM-004 | 요약 생성 이력과 사용 모델·프롬프트 버전을 기록한다. | P1 | 같은 결과를 분석할 수 있는 메타데이터가 저장된다. |

### 5.6 문제 생성과 답안 평가

|---|---|---:|---|
| QUIZ-001 | 객관식 또는 주관식 문제를 생성한다. | P0 | 사용자가 유형, 개수, 난이도 및 주제를 선택할 수 있다. |
| QUIZ-002 | 모든 문제에 정답, 해설과 원문 근거를 저장한다. | P0 | 근거가 없는 문제는 사용자에게 제공하지 않는다. |
| QUIZ-003 | 객관식 보기는 하나의 정답과 타당한 오답으로 구성한다. | P0 | 정답 번호와 표시 순서를 분리해 저장한다. |
| QUIZ-004 | 사용자는 답안을 제출하고 결과를 확인한다. | P0 | 중복 제출 정책에 따라 시도 회차를 보존한다. |
| QUIZ-005 | 객관식은 저장된 정답으로 결정론적으로 채점한다. | P0 | 같은 답안은 항상 같은 결과를 반환한다. |
| QUIZ-006 | 주관식은 기준 답안·채점 기준·근거를 이용해 평가한다. | P0 | 결과를 `AI 평가`로 표시하고 점수와 함께 부족한 핵심어를 설명한다. |
| QUIZ-007 | 틀리거나 헷갈림으로 표시한 문제를 오답 목록에 저장한다. | P0 | 문제, 최근 답안, 해설과 재도전 횟수를 조회할 수 있다. |
| QUIZ-008 | 오답 문제를 다시 풀고 정답률 변화를 확인한다. | P0 | 시도별 답안과 채점 결과를 보존한다. |

### 5.7 화면 요구사항

| 화면 | 필수 내용 |
|---|---|
| 회원가입·로그인 | 입력 검증, 오류 메시지, 로딩 상태 |
| 대시보드 | 문서 목록, 업로드, 처리 상태, 최근 학습 |
| 문서 상세 | 원본 정보, 처리 단계, 요약, 문제 생성 진입, 삭제 |
| PDF 근거 뷰어 | 페이지 이동, 인용 문맥 강조 |
| 요약 | 전체·주제 요약, 근거 링크, 생성 상태 |
| 문제 풀이 | 객관식·주관식 입력, 진행률, 제출 확인 |
| 결과 | 정오답, 해설, 근거, 헷갈림 표시 |
| 오답 노트 | 필터, 재도전, 시도 이력 |

모든 화면은 데스크톱과 모바일 웹의 기본 반응형 레이아웃을 제공한다. 접근성의 최소 기준으로 키보드 탐색, 입력 레이블, 포커스 표시 및 색상 외 상태 표현을 적용한다.

## 6. 비기능 요구사항

### 6.1 보안과 개인정보

- 비밀번호는 검증된 비밀번호 해시 알고리즘으로 저장한다.
- 인증·인가 검사는 프론트엔드가 아닌 서버에서 강제한다.
- 파일명은 저장 경로로 직접 사용하지 않고 서버가 저장 키를 생성한다.
- 악성 확장자, 경로 조작 및 허용량 초과 업로드를 거부한다.
- API 키와 데이터베이스 자격 증명을 소스 저장소에 커밋하지 않는다.
- 로그에 비밀번호, 토큰, PDF 본문 및 전체 LLM 프롬프트를 그대로 남기지 않는다.
- 사용자 삭제 및 문서 삭제 시 외부 벡터 저장소와 객체 저장소 데이터도 삭제한다.
- LLM 제공자에게 전송되는 데이터 범위와 보존 가능성을 사용자에게 알린다.

### 6.2 성능

아래 수치는 초기 목표이며 테스트 환경과 측정 조건을 성능 보고서에 함께 기록한다.

- 일반 조회 API: 동시 사용자 20명 조건에서 p95 500ms 이하
- 업로드 완료 후 작업 접수 응답: p95 2초 이하(파일 전송 시간 제외)
- 처리 상태 조회: p95 300ms 이하
- PDF 처리는 요청 스레드를 점유하지 않고 비동기로 수행
- 문서 처리 시간은 페이지 수, 모델, 토큰 수 및 외부 API 대기 시간과 함께 기록

### 6.3 신뢰성과 복구

- 외부 API 호출에는 연결·응답 타임아웃을 적용한다.
- 재시도 가능한 오류와 재시도하면 안 되는 오류를 구분한다.
- 재시도와 중복 전달을 고려해 작업과 결과 저장을 멱등하게 만든다.
- 실패한 작업의 단계, 오류 코드, 시도 횟수 및 마지막 변경 시각을 보존한다.
- 데이터베이스 장애, LLM 시간 초과, 임베딩 실패 및 잘못된 PDF에 대한 실패 시나리오를 테스트한다.

### 6.4 관측 가능성

- 모든 요청에 상관관계 ID를 부여한다.
- 사용자 ID는 원문 값 대신 추적 가능한 비식별 값으로 로깅한다.
- 최소 메트릭: 요청 수·오류율·응답 시간, 작업 상태별 개수, 처리 시간, 재시도·실패 수, LLM 토큰·비용, 검색 지연 시간
- 최소 대시보드: API 상태, 비동기 작업 상태, 외부 AI 호출 상태
- 핵심 오류에 대한 알림 기준과 대응 방법을 문서화한다.

### 6.5 유지보수성과 테스트

- 백엔드는 도메인 경계를 가진 모듈러 모놀리스로 시작한다.
- 인증, 문서, 처리 작업, RAG, 요약, 문제, 학습 기록 모듈을 분리한다.
- 외부 LLM·임베딩·파일 저장소는 인터페이스 뒤로 격리한다.
- API는 OpenAPI 문서로 제공한다.
- 단위 테스트, 통합 테스트 및 핵심 사용자 흐름 E2E 테스트를 구분한다.
- 테스트 없이 수동 확인만 한 기능은 완료로 처리하지 않는다.

경로와 요청·응답 스키마는 API 설계 단계에서 확정한다.

```text

POST   /api/v1/documents
GET    /api/v1/documents
```

## 9. RAG 품질 요구사항과 평가

### 9.1 평가 원칙

RAG는 하나의 정확도 수치로 판단하지 않고 다음 두 단계를 분리한다.

1. 검색 품질: 정답 근거가 상위 검색 결과에 포함됐는가?
2. 생성 품질: 검색된 근거를 벗어나지 않고 요약·문제·해설을 만들었는가?

### 9.2 최소 평가 데이터셋

- 공개 사용이 가능하거나 직접 만든 샘플 PDF 3개 이상
- PDF별 사실 질문과 근거 페이지를 포함한 골든 질문 총 30개 이상
- 쉬운 사실 검색, 여러 문단 결합, 문서에 답이 없는 질문을 포함
- 평가 데이터와 서비스 데모 데이터의 사용 권한을 기록

### 9.3 최소 측정 항목

- 검색: `Recall@k`, 근거 페이지 적중률, 검색 지연 시간
- 생성: 근거 충실도, 답변 관련성, 인용 정확성, 답변 불가 판단 성공률
- 운영: 요청당 토큰 수, 추정 비용, 전체 처리 시간, 실패율

LLM 기반 자동 평가는 참고값으로 사용하고, 표본에 대한 사람 검토 결과를 함께 기록한다.

## 10. 인수 테스트 시나리오

1. 정상 PDF 업로드 후 모든 처리 상태를 거쳐 `READY`가 된다.
2. 손상된 PDF와 텍스트가 없는 스캔 PDF는 명확한 사유로 실패한다.
3. 외부 임베딩 API가 일시 실패하면 재시도 후 성공하거나 최종 실패 상태가 된다.
4. 동일 작업 메시지가 두 번 전달돼도 청크·벡터·요약이 중복 생성되지 않는다.
5. 사용자 A는 사용자 B의 문서 ID를 알아도 조회·삭제할 수 없다.
6. 요약의 인용을 선택하면 올바른 PDF 페이지와 문맥이 열린다.
7. 객관식 정답은 반복 제출해도 같은 기준으로 채점된다.
8. 주관식 평가에는 점수, 기준 답안, 부족한 내용 및 근거가 표시된다.
9. 틀린 문제는 오답 목록에 나타나고 재도전 이력이 누적된다.
10. 문서 삭제 후 원문, 청크, 벡터, 요약, 문제와 답안을 조회할 수 없다.
11. 애플리케이션 재시작 후에도 완료·실패 작업의 상태를 조회할 수 있다.
12. 핵심 흐름을 브라우저 E2E 테스트로 재현할 수 있다.

1. 사용량 계측을 기반으로 무료 한도와 유료 상품 정의
2. PG 결제, 웹훅 검증, 결제 멱등성, 구독 상태 및 환불
3. 다중 PDF 과목과 개인화 취약 영역 분석
4. OCR 및 입력 형식 확장
5. 하이브리드 검색·Reranker 및 평가 자동화
6. 강사·교육기관용 기능과 멀티테넌시

결제는 학습 흐름과 사용량 계측이 검증된 뒤 도입한다. PG 연동 완료는 단순 결제 성공 화면이 아니라 서버 웹훅 검증, 중복 이벤트 처리, 취소·환불 및 권한 반영까지 포함해 별도 명세한다.

## 14. 가정과 열린 질문

### 14.1 현재 가정

- MVP는 개인 학습자 한 명의 단일 PDF 학습 흐름에 집중한다.
- 프론트엔드는 React 기반의 기본 반응형 웹으로 구현한다.
- 백엔드는 Spring Boot 기반 모듈러 모놀리스로 시작한다.
- AI 처리는 외부 LLM·임베딩 API를 사용하되 제공자 교체가 가능하게 격리한다.
- 처리 상태는 MVP에서 폴링으로 조회한다.
- PG 결제는 MVP에 포함하지 않는다.

### 14.2 설계 단계에서 확정할 질문

- Java와 Spring Boot의 기준 버전
- React 빌드 도구와 상태 관리 방식
- 관계형 데이터베이스와 벡터 저장 방식
- 원본 PDF 저장소(로컬 개발과 배포 환경)
- 비동기 메시지 브로커와 워커 배포 방식
- 사용할 LLM·임베딩 모델과 월 비용 상한
- 액세스·갱신 토큰의 저장 및 폐기 정책
- 주관식 점수 체계와 사용자 이의 제기 방식
- 배포 플랫폼과 예상 운영 예산
- 업로드 파일의 기본 보존 기간

열린 질문은 구현 중 암묵적으로 결정하지 않고 ADR 또는 상세 설계 문서에 결정 근거와 함께 기록한다.
