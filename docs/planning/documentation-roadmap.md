# AiProfessor 문서 작업 로드맵

- 작성일: 2026-11-02
- 기준: MVP를 빠르게 개발하되 구현·검증되지 않은 내용을 문서에서 확정적으로 표현하지 않는다.

## 1. 현재 완료된 기준 문서

아래 문서는 개발 기준선으로 사용한다. 코드 작성 전에 한 번 커밋해 문서 기준점을 남긴다.

| 문서 | 상태 | 역할 | 개발 중 변경 기준 |
|---|---|---|---|
| MVP 요구사항 명세서 | 완료 | MVP 목표, 포함·제외 범위, 완료 조건 정의 | 요구사항 변경 시 버전과 변경 이유 기록 |
| MVP 테이블 명세서 | 완료 | 16개 테이블, 컬럼, 키, 관계 정의 | Flyway DDL과 달라지면 함께 갱신 |
| MVP API 명세서 | 완료 | 인증·문서·RAG·학습 API 계약 정의 | OpenAPI와 달라지면 함께 갱신 |
| Notion 형식 API 목록 | 완료 | Notion 데이터베이스 관리용 API 목록 | API 추가·삭제 시 행 단위 갱신 |
| ERD PDF | 완료 | 테이블과 관계 시각화 | FK·테이블 구조 변경 시 재생성 |
| ADR-001~006 | 완료 | MVP 아키텍처 선택, 대안, 단점과 재검토 조건 기록 | 결정 변경 시 기존 ADR 상태 변경 및 새 ADR 추가 |

## 2. 개발 시작 전 작성할 문서

개발을 막는 결정만 기록한다. 권장 소요 시간은 전체 1일 이내다.

### 2.1 기술 선택 ADR

작성 경로: `docs/decisions/README.md` 및 `ADR-001`~`ADR-006`

상태: 2026-11-04 작성 완료. 모델명·월 비용 상한·임베딩 차원·pgvector 인덱스 종류처럼 실험이 필요한 값은 검증 예정으로 유지한다.

| 결정 항목 | 반드시 기록할 내용 |
|---|---|
| Java·Spring Boot | 사용할 버전과 선택 이유 |
| React | 빌드 도구, TypeScript 사용 여부, 상태 관리 범위 |
| 데이터베이스 | PostgreSQL 및 pgvector 채택 여부 |
| PDF 저장소 | 로컬 개발과 배포 환경의 저장 방식 |
| 비동기 처리 | 메시지 브로커, Worker 실행·재시도 방식 |
| 인증 | Access·Refresh Token 저장, 회전, 폐기 정책 |
| AI 모델 | LLM·임베딩 제공자, 교체 전략, 비용 상한 |
| 배포 | 배포 플랫폼과 예상 월 운영비 |

완료 기준:

- 각 항목의 선택안, 대안, 선택 이유와 단점을 한 문단 이내로 기록한다.
- 아직 실험이 필요한 선택은 `확정`이 아니라 `가설·검증 예정`으로 표시한다.

### 2.2 시스템 아키텍처·모듈 경계

권장 경로: `docs/architecture/mvp-system-architecture.md`

필수 내용:

```text
React
  → Spring Boot API
  → PostgreSQL/pgvector
  → PDF Object Storage
  → Message Broker
  → Worker
  → LLM/Embedding Provider
```

- 인증, 문서, 작업, RAG, 요약, 문제, 학습 기록 모듈의 책임
- 모듈 사이 허용 의존 방향
- 외부 저장소·AI 제공자 인터페이스 경계
- API 프로세스와 Worker의 배포 단위

완료 기준:

- 구성요소 그림 1개와 모듈별 책임 표가 있다.
- 어떤 모듈이 DB 테이블을 소유하는지 설명할 수 있다.

### 2.3 비동기 처리 시퀀스

권장 경로: `docs/architecture/pdf-processing-sequence.md`

필수 흐름:

```text
PDF 업로드
  → 파일 검증·저장
  → Document/Job 생성
  → 202 + jobId 반환
  → Worker 수신
  → 텍스트 추출
  → 청킹
  → 임베딩
  → READY 또는 FAILED
  → 클라이언트 상태 조회
```

함께 표시할 실패 흐름:

- 잘못된 PDF
- 외부 임베딩 API 시간 초과
- 메시지 중복 전달
- Worker 중단과 재시작
- 최대 재시도 초과

완료 기준:

- 정상 흐름과 최소 3개 실패 흐름이 있다.
- 트랜잭션 경계와 멱등성 키 적용 위치가 표시된다.

### 2.4 MVP 개발 백로그

권장 경로: `docs/planning/mvp-backlog.md` 또는 GitHub Issues

| Epic | 주요 작업 | 완료 증거 |
|---|---|---|
| 프로젝트 초기 구성 | 멀티 프로젝트 구조, Docker Compose, 환경변수, CI | 로컬 실행 및 CI 성공 |
| 인증·인가 | 회원가입, 로그인, 갱신, 로그아웃, 소유권 | 통합 테스트 |
| 문서 관리 | PDF 검증, 저장, 조회, 삭제 | 브라우저 업로드 시연 |
| 비동기 처리 | Job 상태, Worker, 재시도, 멱등성 | 실패·중복 테스트 |
| RAG·요약 | 추출, 청킹, 임베딩, 검색, 인용 | 골든 질문 평가 |
| 문제·학습 | 문제 생성, 채점, 오답, 재도전 | E2E 테스트 |
| 운영·배포 | 로그, 메트릭, 비용, 배포 자동화 | 배포 URL과 운영 문서 |

완료 기준:

- 모든 작업이 요구사항 ID와 연결된다.
- 각 작업은 0.5~2일 안에 완료 가능한 크기로 나눈다.
- `코드 작성`이 아니라 테스트·화면·로그 같은 완료 증거를 적는다.

## 3. 개발하면서 작성할 문서

구현 또는 실험 결과가 생긴 시점에 작성한다. 개발 전에 빈 문서를 길게 채우지 않는다.

| 문서·산출물 | 작성 시점 | 반드시 포함할 내용 |
|---|---|---|
| Flyway Migration | 테이블 구현 시 | 실제 DDL, 인덱스, FK, 변경 순서 |
| OpenAPI/Swagger | API 구현 시 | 요청·응답, 상태 코드, 인증, 예시 |
| 테스트 전략 | 첫 통합 테스트 작성 시 | 단위·통합·E2E 범위와 테스트 환경 |
| RAG 평가 문서 | 첫 검색 기능 완성 시 | 데이터셋, Recall@k, 인용 정확성, 비용·지연 |
| 장애·복구 기록 | 재시도 구현 시 | 실패 조건, 로그, 재시도 결과, 멱등성 검증 |
| 성능 테스트 보고서 | 수직 기능 완성 후 | 환경, 데이터, 동시 사용자, 반복 횟수, 원시 결과 |
| 배포 Runbook | 첫 배포 시 | 배포·롤백·환경변수·장애 확인 방법 |
| 보안 점검표 | 인증·파일 업로드 완료 시 | 토큰, 소유권, 파일 검증, 비밀값, 로그 노출 |
| 비용 보고서 | AI 연동 후 | 모델별 토큰, 요청당 추정 비용, 월 상한 |
| 블로그 개발 기록 | 기능 단위 완료 후 | 문제, 선택지, 구현, 실패, 테스트 조건, 한계 |

| 운영 대시보드 설명 | 관측 가능성 증명 | API·Job·AI 호출 메트릭과 알림 기준 설명 |

## 5. MVP 이후 작성할 문서

현재 개발을 시작하기 위해 작성할 필요가 없다.

| 문서 | 작성 조건 |
|---|---|
| PG 결제·구독 명세 | 무료 사용량과 유료 상품을 결정한 뒤 |
| 결제 상태·웹훅 시퀀스 | PG사를 선정한 뒤 |
| OCR 설계 | 스캔 PDF 지원을 실제 우선순위로 정한 뒤 |
| 다중 PDF 과목 설계 | 단일 PDF 학습 흐름을 검증한 뒤 |
| 개인화·간격 반복 설계 | 충분한 학습 이력이 쌓인 뒤 |
| 강사·기관 멀티테넌시 | B2B 사용자를 검증한 뒤 |
| MSA 분리 설계 | 모듈별 부하·배포 독립 요구가 측정된 뒤 |

## 7. 바로 다음 진행 순서

1. 현재 문서와 ERD를 기준선으로 커밋한다.
2. P0 문서 4개를 하루 이내에 작성한다.
3. Spring Boot·React 프로젝트를 생성한다.
4. `회원가입·로그인 → PDF 업로드` 수직 기능부터 구현한다.
5. 구현과 동시에 Flyway·OpenAPI·테스트를 갱신한다.

문서 작성 자체를 완료 조건으로 삼지 않는다. 실제 코드, 테스트, 로그, 실행 화면 및 측정 결과와 연결된 문서만 직접 경험의 증거로 사용한다.
