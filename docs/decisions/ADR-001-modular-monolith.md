# ADR-001: Spring Boot 모듈러 모놀리스 채택

- 상태: 승인
- 결정일: 2026-11-04
- 적용 범위: MVP 백엔드 구조
- 관련 문서: `docs/requirements/mvp-requirements.md`

## 배경

AiProfessor는 Django 기반 서비스를 Spring Boot와 React로 마이그레이션한다. MVP는 인증, PDF 문서, 처리 작업, RAG, 요약, 문제 생성, 채점과 오답 학습을 제공해야 한다. 각 기능의 책임은 분리해야 하지만 초기 사용자 수와 팀 규모가 작고, AWS 실배포 비용과 개발 속도가 우선이다.

MSA를 먼저 적용하면 서비스별 배포, 네트워크 통신, 분산 추적, 데이터 일관성, 장애 복구와 운영 자동화가 개발 범위에 추가된다. 현재는 이러한 비용을 정당화할 독립적인 확장·배포 요구가 측정되지 않았다.

## 결정 기준

- MVP를 빠르게 완성하고 하나의 트랜잭션으로 처리할 수 있어야 한다.
- 기능 경계를 코드와 데이터 소유권으로 명확히 나눠야 한다.
- PDF Worker는 API 요청과 별도로 실행·확장할 수 있어야 한다.
- 외부 저장소와 AI 제공자를 교체할 수 있어야 한다.
- 향후 측정된 필요가 생기면 특정 모듈을 서비스로 분리할 수 있어야 한다.

## 검토한 선택지

| 선택지 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 계층형 단일 애플리케이션 | 구현이 가장 단순함 | 도메인 간 결합이 커지기 쉬움 | 제외 |
| 모듈러 모놀리스 | 단일 배포·트랜잭션을 유지하면서 경계를 강제 가능 | 경계를 지속적으로 검증해야 함 | 선택 |
| MSA | 서비스별 독립 배포·확장 가능 | 초기 비용, 분산 장애와 데이터 일관성 복잡도 증가 | MVP 이후 재검토 |

## 결정

Spring Boot 백엔드를 모듈러 모놀리스로 구현한다. API와 Worker는 같은 코드베이스와 도메인 모듈을 사용하되 서로 다른 실행 프로필과 컨테이너로 구동할 수 있게 한다.

초기 모듈은 다음과 같다.

| 모듈 | 책임 |
|---|---|
| `auth` | 회원, 인증, 토큰 회전·폐기, 권한 |
| `document` | PDF 검증, 메타데이터, 저장소 키, 소유권, 삭제 |
| `job` | 비동기 작업 상태, 실행 이력, 재시도, Outbox |
| `rag` | 텍스트 추출, 청킹, 임베딩, 검색, 인용 근거 |
| `summary` | 전체·주제 요약과 인용 |
| `quiz` | 문제 묶음, 객관식·주관식 문제, 근거 |
| `learning` | 답안, 채점 결과, 오답과 재학습 |
| `ai` | LLM·임베딩 포트, 사용량·비용 기록 |

### 경계 규칙

- 다른 모듈의 Repository나 내부 Entity를 직접 사용하지 않는다.
- 모듈 간 호출은 공개 Application Service 또는 명시적인 이벤트 계약을 통한다.
- 각 테이블의 변경 책임은 하나의 모듈이 소유한다.
- S3, SQS, LLM과 임베딩 제공자는 포트·어댑터 경계 뒤에 둔다.
- 공통 모듈에는 식별자, 시간, 오류 응답처럼 실제로 공통인 요소만 둔다.
- 패키지 의존 규칙은 아키텍처 테스트로 검증한다.

## 결과

### 긍정적 결과

- 단일 PostgreSQL 트랜잭션과 단일 코드베이스로 MVP 복잡도를 낮춘다.
- API와 Worker를 독립 프로세스로 실행해 PDF 작업 부하를 분리할 수 있다.
- 도메인 경계와 외부 포트를 유지하면 이후 서비스 분리 비용을 낮출 수 있다.

### 감수할 결과

- 잘못된 참조가 누적되면 모듈 경계가 형식적으로만 남을 수 있다.
- API와 Worker가 같은 릴리스 단위를 공유하므로 완전한 독립 배포는 아니다.
- 초기 단일 DB가 모든 모듈의 공통 장애 지점이 된다.

## 검증 계획

- 모듈별 패키지와 소유 테이블을 시스템 아키텍처 문서에 명시한다.
- 다른 모듈의 Repository 직접 참조를 금지하는 아키텍처 테스트를 작성한다.
- 동일 빌드 결과물을 API와 Worker 프로필로 각각 실행하는 통합 테스트를 수행한다.

## 재검토 조건

- 특정 모듈의 부하가 다른 모듈과 독립적으로 확장되어야 한다.
- 팀별 독립 배포가 반복적으로 필요해진다.
- 장애 격리 또는 규제상 데이터 분리가 요구된다.
- 모듈별 릴리스 주기 차이가 단일 배포의 병목으로 측정된다.
